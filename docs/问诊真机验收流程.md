# 问诊真机验收流程

本文是 Ditan 问诊后端在 Android 和 HarmonyOS 上的真机验收步骤，供测试时逐项对照。设计见[四诊问诊后端迁移设计](四诊问诊后端迁移设计.md)。两端仓库中已有的验收清单（Android `refect_document/15_重构执行总方案与回归清单.md` 的 T10 记录、HarmonyOS `docs/问诊后端接入验收.md`）均已包含在下列用例中。

## 总体安排

| 轮次 | 环境 | 模型 | 目的 |
| --- | --- | --- | --- |
| 1 | 测试用 Ditan | 假模型 | 主流程和各个分支走得通 |
| 2 | 同上 | 假模型 | 断网、杀 App、重连等故障能恢复，身份不串 |
| 3 | 同上 | 真实 deepseek-flash | 问法、报告质量和响应速度 |
| 4 | 生产环境 | 真实模型 | 测试机构冒烟，然后灰度 |

前三轮使用单独的测试 Ditan，测试数据不会进入生产库。假模型的输出固定、不产生费用，出问题时也容易定位，所以故障测试都在假模型上完成。

## 准备工作

1. **合并 Apkio 的 PR**。它只新增问诊票据接口，风险很低；客户端要先从 Apkio 取到票据，才能调用问诊接口。
2. **启动测试用的 Ditan**（内网服务器或开发机均可）：
   - 用 docker compose 启动数据库和服务，执行 `alembic upgrade head`；
   - 配置 `CONSULTATION_LLM_PROVIDER=fake`，`APKIO_BASE_URL` 指向已上线问诊票据的 Apkio；
   - 测试机必须能访问该地址。客户端可能要求 HTTPS，这时需要内网 HTTPS 或测试域名。
3. **打测试包**：
   - Android：`local.properties` 中设置 `CONSULTATION_BACKEND=ditan`，`PATIENT_UPLOAD_BASE_URL` 指向测试 Ditan；
   - HarmonyOS：同样两项，再运行 `scripts/generate-local-config.ps1` 生成配置；
   - 两端各打一个测试包。
4. **账号和设备**：
   - 测试机构 A 准备两个操作员账号，测试机构 B 准备一个账号；
   - 至少两台 Android、一台鸿蒙；测试多设备同时回答需要两台。
5. **合成患者**：面舌脉用测试人员本人采集，二维码资料使用合成数据，覆盖以下六类：

| 患者 | 期望问题数 | 说明 |
| --- | ---: | --- |
| 男，30 岁 | 11 | 只有主线问题 |
| 女，25 岁 | 15 | 主线 11 题，加孩子、月经、血块与痛经、白带 |
| 女，15 岁 | 14 | 不问是否有孩子 |
| 女，8 岁 | 11 | 小于 10 岁，不进入女性分支 |
| 性别缺失或写成"未知" | 11 | 按未知性别处理，不进入女性分支 |
| 女，生日缺失 | 14 | 年龄未知，按"非小孩、未满 20 岁"处理 |

## 第 1 轮：主流程和分支（两端都做）

- [ ] 每位合成患者完整走一遍：开场 → 全部问题 → 获取报告 → 报告 → 上传病历。
- [ ] 问题个数与上表一致；开场只出现一次，报告只生成一次。
- [ ] 界面状态与问诊进度一致："请回答医生的问题"、"可以生成报告"、"报告生成中"、"报告已保存"。
- [ ] 报告生成后，用 encounter_uuid 在 Ditan 的病历表中查到记录，核对报告正文和 `User:` / `AI:` 格式的对话记录。
- [ ] 一份超过 1024 字的报告能上传成功。

## 第 2 轮：故障与恢复（重点）

| | 操作 | 期望结果 |
| --- | --- | --- |
| [ ] | 识别出回答、刚点发送时杀掉 App 后重进 | 自动补发这条回答，只推进一次；回复显示但不自动播报 |
| [ ] | 回复播到一半时杀掉 App 后重进 | 显示完整回复，不自动重播，问诊继续 |
| [ ] | 报告生成中杀掉 App 后重进 | 报告继续生成或已完成，只有一份 |
| [ ] | 提交回答的瞬间断网，恢复网络后重试 | 同一轮只推进一次，不出现重复的问题 |
| [ ] | 报告已完成但保存归档时断网 | 恢复网络后报告能补存，并能上传 |
| [ ] | 重启设备后进入该患者 | 与杀 App 后的表现一致 |
| [ ] | 数字人断开或点刷新 | 问诊不从头开始；旧语音不在新连接上播出 |
| [ ] | 点"重播" | 只重播上一句，不重新调用模型 |
| [ ] | 一轮处理中途重启测试 Ditan | 这一轮约 1 分钟后超时，之后点重试（可能需要两次）能接续，只推进一次 |
| [ ] | 停在一个问题上超过 5 分钟再回答 | 自动换票据，问诊照常继续 |
| [ ] | 连续点"获取报告" | 报告只生成一次 |
| [ ] | 在可以生成报告时口头说"获取报告"或其他话 | 按普通回答记录，并再次提示点按钮 |
| [ ] | 两台设备同时回答同一患者（需两台设备打开同一患者草稿，做不到可跳过） | 只有一个成功，另一台刷新到最新状态 |
| [ ] | 同机构换账号、切换到机构 B、退出登录 | 旧患者的画面、语音和待发内容不出现在新身份下 |
| [ ] | 在别处放弃这次问诊（可直接调用 `POST /api/v1/consultations/{id}/abandon` 模拟） | 本机下一轮不卡死，状态刷新为"问诊已放弃" |

## 第 3 轮：真实模型

1. 测试 Ditan 改为 `CONSULTATION_LLM_PROVIDER=openai`，模型 `deepseek-flash`。
2. 每端至少做 5 次完整问诊，覆盖男女分支。
3. 检查项：
   - [ ] 问题切题，开头的承接语与患者上一轮回答相符；
   - [ ] 从说完到开始播报不超过约 2 秒；
   - [ ] 没有降级成念固定问题；
   - [ ] 报告由医生审阅：纯文本、无 Markdown、不给治疗建议，证型与依据合理。

## 第 4 轮：生产冒烟与灰度

1. 确认 GitHub Secret `AI_MODEL_NAME=deepseek-flash`，服务器 nginx 已对问诊流式接口关闭缓冲（见 DitanBackend `docs/DEPLOYMENT.md`），再合并 Ditan 的 PR。合并后会自动部署，并在备份数据库后执行迁移。
2. 用测试机构在生产环境走一遍完整问诊，并做一次断网恢复。这一步要验证经过 nginx 的流式输出，测试环境通常不经过 nginx。
3. 灰度：问诊开关在打包时设定，因此把开启 `ditan` 的安装包通过 Apkio 的白名单发布给指定机构。
4. 灰度期间验证回退：新建就诊切回 Coze 正常；已在 Ditan 开始的问诊继续在 Ditan 完成。

## 排查方法

测试时记下患者的 encounter_uuid。数据库中的时间为 UTC。

```sql
-- 找到这次问诊
SELECT id, status, version FROM consultations WHERE encounter_uuid = '…';

-- 每一轮的状态：失败原因、是否被接管（attempt > 1）
SELECT turn_id, kind, status, attempt, error_code, created_at, completed_at
FROM consultation_turns WHERE consultation_id = '…' ORDER BY id;

-- 完整对话；meta 中 fallback 为 true 表示这一题用了固定问题
SELECT seq, role, step_id, content, meta
FROM consultation_messages WHERE consultation_id = '…' ORDER BY seq;

-- 模型调用：首字耗时、总耗时、输入 token；问偏时看 request 字段中发给模型的原文
SELECT step_id, purpose, status, first_token_ms, latency_ms, prompt_tokens
FROM consultation_llm_calls WHERE consultation_id = '…' ORDER BY id;
```

客户端日志：Android 用 `adb logcat`，HarmonyOS 用 `hdc hilog`。

## 附：无需真机的部署预演（2026-10-04，已完成）

在本机用 Docker 按生产形态搭建了一套环境：Ditan 镜像由正式 Dockerfile 构建，以 4 个 worker 运行；PostgreSQL 17 由 migrate 服务从空库执行到最新迁移；前面放 nginx（一个入口按部署文档配置，另一个入口全部使用 nginx 默认设置）；Apkio 验票用本地模拟服务代替。全部请求经 nginx 发出，共 27 项检查全部通过。环境已删除。

| 类别 | 检查结果 |
| --- | --- |
| 迁移 | 000 到 005 在容器中顺序执行成功 |
| 主流程（假模型） | 男 30 岁、女 25 岁、女 15 岁、女 8 岁、性别缺失、女生日缺失的问题数分别为 11、15、14、11、11、14，报告、归档格式正确 |
| 鉴权与隔离 | 无票据 401；跨机构 404；同机构其他操作员可读；Apkio 不可用时 503，恢复后正常 |
| 幂等与并发 | 同一 turn_id 重发结果相同、不重复写消息；内容不同 409；过期版本 409 并附快照；两台设备同时回答只成功一个 |
| 负载 | 20 个问诊（340 轮）并发完成用时 3.5 秒；服务端单轮处理中位数 8.8 毫秒 |
| 真实模型 | 11 问无降级；提问首字中位数约 0.6 秒、P95 约 1 秒；报告首字约 17 秒、约 20 秒完成 |
| nginx | 按文档配置与完全默认配置，报告都能逐段流式送达（服务端返回 `X-Accel-Buffering: no` 并每 15 秒发心跳） |
| 断开重连 | 收到 accepted 后断开，再用同一 turn_id 请求，能拿到结果且只有一份报告 |
| 停止容器 | 报告生成中执行 `docker compose stop`，容器等报告完成后退出（18 秒），报告完整 |
| 强杀容器 | 报告生成中 `kill` 容器，轮次保持处理中、没有半份报告；约 180 秒超时后同一 turn_id 重试被接管（attempt 2）并完成，只有一份报告 |

由此，真机测试只需关注客户端相关的部分：界面状态、录音与播报、杀 App 与断网恢复、身份切换，以及真实网络下的表现。

**已决定**：报告首字约 17 秒，主要是 deepseek-flash 默认的思考过程（原 Coze 报告节点使用不带思考的 DeepSeek-V3）。所有者决定报告保留思考模式，约 17 秒的等待可以接受，期间界面显示"报告生成中"。真机测试时确认这段等待中界面状态清楚、没有误判为卡死。
