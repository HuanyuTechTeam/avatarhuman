## 9. 自建后端实现设计（建议，不是原配置）

### 9.1 用可暂停、可恢复的执行器承接多轮问答

模型节点生成问题后，问答节点需要等待用户输入。建议为每次运行持久化状态；收到回答后从等待节点继续执行，避免用单个持续占用连接的请求覆盖整次问诊。

建议运行状态：`running`、`waiting_for_user`、`completed`、`failed`。

```text
运行记录：run_id、workflow_version、conversation_id、status、current_node_id
节点结果：run_id、node_id、attempt、inputs、outputs、status
待答问题：question_id、run_id、node_id、question_text、status
消息记录：message_id、conversation_id、role、content、created_at、sequence
```

上述是目标后端的数据模型建议，不能当作 Coze `QUESTION_DATA` 的原始结构。

### 9.2 保留节点作用域

```text
outputs[node_id][field_name]
```

不要用一个全局 `output` 存放全部节点结果。迁移输入绑定时显式记录：

```yaml
input_bindings:
  output:
    source_node: 待核实的上游节点ID
    source_field: output
```

### 9.3 建议的接口契约

| 接口  | 用途  |
| --- | --- |
| `POST /workflow-runs` | 提交 `USER_INPUT`、`CONVERSATION_NAME`，启动执行 |
| `GET /workflow-runs/{run_id}` | 返回执行状态、当前问题或最终结果 |
| `POST /workflow-runs/{run_id}/answers` | 提交 `question_id`、回答及幂等键，恢复执行 |

回答接口应验证问题属于当前运行且处于待答状态；重复提交不能推进两次。模型调用重试与恢复也应防止重复生成同一轮问题。

### 9.4 模型替换

把 Coze 模型调用封装为统一的模型适配器。先补录原模型配置和提示词，再选择自建后端的模型端点。显示名称“扣子-deepseek”不足以确定具体 API 模型 ID，也不能保证换用同名模型后输出相同。

### 9.5 消息历史

用自建消息库承接查询节点的职责，同时明确消息角色、排序、分页和截断策略。`hasMore=true` 时是否需要继续读取应根据原配置和报告需求决定，不能静默忽略历史。
