# 问诊后端迁移执行计划

本文是交给执行代理（GPT/Codex）的任务清单，用来落地 [四诊问诊后端迁移设计](四诊问诊后端迁移设计.md)（下称"设计文档"）。设计文档负责回答"做成什么样"，本文负责"按什么顺序做、改哪些文件、怎样算做完"。两者冲突时以设计文档为准。

## 0. 执行规则（每个任务都适用）

### 0.1 先读的材料

1. 设计文档全文，重点是第 4～11 节。
2. [Coze 工作流详细信息](coze工作流详细信息.md)的第 13～15 节（提示词原文）。
3. 动到哪个仓库，就先读该仓库的代理规则：
   - MCT_Android：`agent.md`、`CLAUDE.md`、`refect_document/15_重构执行总方案与回归清单.md`。`agent.md` 要求 TDD、接口一致性检查，并在 15 号文档的"执行回归记录"中回写结论，这些都必须遵守。
   - Apkio：`CODEX.md`（工作日志，任务完成后追加一条记录）。
   - MCT_Harmonyos：`README.md`（本机配置、测试命令）。
   - DitanBackend：`README.md`、`docs/API.md`、`docs/DEPLOYMENT.md`。

### 0.2 分支、提交与边界

- 每个仓库都从 `main` 新建分支 `feature/consultation-backend`，不要直接提交到 `main`，也不要 push、合并或部署。
- Android 的 `agent.md` 要求以 `refector_main` 为基座分支，但该分支在本地和远端都已不存在。本次改为从 `main` 建分支，并在 15 号文档的执行回归记录中注明这一点。
- MCT_Harmonyos 工作区里有一处未提交的 `build-profile.json5` 修改：签名配置的字段顺序变了，签名密码的密文也与已提交的版本不同（可能是 DevEco 在本机重新加密过）。还原它可能导致本机签名构建失败，因此不要还原，也不要把它混进任何功能提交，保持原样即可。新建分支时它会留在工作区里，这是正常的。
- 一个任务至少一个提交，提交信息使用 Conventional Commits（例如 `feat(consultation): add turn service`），DitanBackend 用 commitizen 管理版本，必须遵守这一格式。
- 禁止事项：
  - 不修改现有病历上传协议（`POST /api/v1/medical-record` 的请求、响应和重传规则）；
  - 不删除客户端现有的 Coze 路径，新旧路径用开关切换；
  - 不吊销 Coze 令牌，不改生产配置，不访问生产数据库；
  - 不对设计文档未规定的业务规则自行做主，遇到时停下来，在汇报中列出问题；
  - 测试中不发起真实网络请求（DitanBackend 的 `tests/conftest.py` 已拦截，模型一律用假实现）。

## T4 DitanBackend：v1 流程定义、提示词与渲染（纯函数，不访问数据库）

**目标**：实现设计文档 4.3～4.7 中与数据库无关的部分。

**改动**：

  - 提供 `first_step(ctx)` 和 `next_step(current_step_id, ctx)`，返回提问步骤或获取报告节点。
- `app/services/consultation/prompts/v1/`：从详细信息文档第 15 节逐字复制 L03～L18 的提示词（不含 L01、L02），每个节点一个 `.txt` 文件，文件名形如 `L03_core_history.txt`。唯一允许的修改是把 `{{USER\_INPUT}}` 改为 `{{USER_INPUT}}`。文件统一使用 UTF-8、LF 换行。
- 固定问题：取提示词中"以下为你要提问的问题。"之后第一个非空行，并去掉首尾空白（L18 的问题末尾有一个空格）。
- 提示词拆分（设计文档 4.5）：提示词文件保存原文，渲染时按规则拆成 system 和 user 两部分。
  - 提问节点：以 `患者信息{{USER_INPUT}}` 这一行为界，这一行之前的部分去掉末尾空行后作为 system，从这一行到结尾作为 user。
  - L14：从 `以下为患者和医生的所有对话记录：` 这一行到 `{{USER_INPUT}}` 这一行（含）作为 user；其余部分作为 system，前后两段之间保留一个空行。
  - system 部分不得含有任何占位符，占位符只能出现在 user 部分。
  - 渲染函数返回 `(system_text, user_text)`。
- 模板渲染：只替换 `{{USER_INPUT}}`、`{{output}}`、`{{input}}`、`{{messageList}}` 四个占位符，用一次正则替换完成，保证插入的内容中即使含有 `{{...}}` 也不会被再次展开。提示词中出现未声明的占位符时直接报错。
- 患者信息渲染（设计文档 4.6）：
  - 按"[基本信息]、[面部情况分析]、[舌象（正面）分析]、[舌象（舌下）分析]、[脉象情况分析]"分段输出；
  - 基本信息依次为性别、年龄、生日、身高、体重、目标体重，缺失的项不输出；
  - 某项分析文本为空时，整段不输出；
  - 不含姓名和电话（结构化输入里本来也没有这两项）。
- 年龄计算：按北京时间计算周岁，基准日由调用方传入。生日接受 `YYYY-MM-DD`、`YYYY/MM/DD` 和 `YYYYMMDD` 三种格式；无效日期或晚于基准日的生日视为年龄未知。
- 对话记录格式化：按 seq 顺序逐行输出，助手消息写成"医生：…"，用户消息写成"患者：…"。

**测试**：

- 分支矩阵：男、女、性别缺失 × 年龄 9、10、11、19、20、21、未知，逐一断言步骤序列（女性 20 岁及以上多问"是否有孩子"；小于 10 岁不进入女性分支）。
- 每个提示词文件的内容，与详细信息文档中对应的代码块逐字相同（规范化反斜杠后）。测试从 `avatarhuman/docs/coze工作流详细信息.md` 读取不方便时，在 Ditan 仓库的 `tests/fixtures/` 中保存一份原文副本，供测试比对。
- 固定问题的提取结果正确，共 15 个提问步骤。
- 渲染时插入含 `{{output}}` 的患者回答，不会被二次替换。
- 提示词拆分：16 个节点的 system 部分都不含占位符，且不随患者输入变化；system 与 user 两部分的非空行合起来，与原文的非空行逐行一致，没有丢失或重复。
- 年龄计算：生日当天、生日前一天、2 月 29 日出生、无效日期。

## T5 DitanBackend：模型调用适配

**目标**：实现设计文档第 9 节和 4.4 的降级规则。

**改动**：

- `app/services/consultation/llm.py`：定义接口 `stream_question(prompt) -> AsyncIterator[str]` 和 `stream_report(prompt) -> AsyncIterator[str]`。
- 真实实现：复用 `app/services/openai_client.py` 中 `OpenAIChatCompletion` 的 `async_client`，调用时：
  - 使用 `with_options(max_retries=0, timeout=...)`；
  - **不传 `temperature`**（现有 `async_stream_chat` 默认会传 0.7，因此不要直接调用它，而是直接调用 `async_client.chat.completions.create(stream=True, ...)`）；
  - 消息为两条：T4 渲染出的 system 部分作为 system 消息，user 部分作为 user 消息，不附带其他历史消息。
- 时限与重试：
  - 生成问题：`max_tokens=150`，首个 token 10 秒内必须返回，全程不超过 30 秒，失败不重试；
  - 生成报告：全程不超过 150 秒，只在首个 token 返回前失败时重试 1 次。
- 熔断：同一进程内连续 3 次生成问题失败后，60 秒内不再调用模型，直接返回"不可用"。
- 并发：用进程级信号量限制同时进行的模型调用数，配置项 `CONSULTATION_LLM_CONCURRENCY`，默认 8。
- 假实现 `app/services/consultation/llm_fake.py`：输出可预期的文本（例如"【假问题】+固定问题"），并支持注入故障：首个 token 前报错、中途报错、延迟。配置项 `CONSULTATION_LLM_PROVIDER=openai|fake`，默认 `openai`；`fake` 只用于本地和测试。
- 每次调用都写入 `consultation_llm_calls`，包括步骤、模型、提示词版本、请求、响应、耗时、首 token 耗时和 token 数。写入失败只记日志，不影响问诊。

**测试**：用假的 `AsyncOpenAI` 响应断言请求参数（没有 temperature、`max_retries=0`、`max_tokens=150`、消息结构），并覆盖超时、熔断、报告重试的行为。

## T6 DitanBackend：轮次服务与执行器（核心）

**目标**：严格按设计文档 5.2～5.4 实现。这是整个项目最关键的部分。

**改动**：

- `app/services/consultation/service.py`：提供以下方法：
  - `create_or_get(ctx, payload)`：同一机构、同一次就诊已有未放弃的问诊时直接返回；`version == 0` 时可以替换 inputs，否则保持原 inputs 不变；
  - `get_snapshot`、`get_turn`；
  - `submit_turn`：返回一个可以订阅事件的句柄；
  - `abandon`：幂等；有进行中的轮次时，用条件更新把它标为 `cancelled`；
  - `archive`：返回 `diagnosis_result` 和 `conversation_log`（`User: …`、`AI: …` 逐行输出）。
- 各类轮次的受理条件：
  - `start`：仅在 `version == 0` 且状态为 `collecting` 时；
  - `answer`：`version >= 1`，且状态为 `collecting` 或 `ready_for_report`；`text` 去掉首尾空白后不能为空，长度不超过 2000 字；
  - `report`：仅在状态为 `ready_for_report` 时。
- `TURN_ID_CONFLICT` 的判定：同一个 `turn_id` 已存在，但 `kind`，或去掉首尾空白后的 `text` 不同。
- 时限：开场和回答的 `deadline_at` 为 60 秒，任务自身时限 45 秒；报告分别为 200 秒和 180 秒。
- 接管：用一条条件 UPDATE 完成——把 `attempt` 加 1、重设 `deadline_at`、状态改为 `processing`，条件是 `attempt` 等于原值，且状态为 `failed`、或为 `processing` 并且已超时。影响 0 行说明被别人抢先接管，此时按"进行中"处理。
- 提交：严格按设计文档 5.2 第 5 步。用户消息和助手消息在同一事务中写入，seq 连续；`version` 加 1。"仍可写入"的含义是状态不是 `completed` 或 `abandoned`。
- 各类轮次的处理按设计文档 4.4：
  - 开场时渲染并固定 `user_input_text`，初始化 `workflow_state`（`current_step`、`sex`、`age`、`age_basis_date`）。
  - `ready_for_report` 状态下的回答：记录这段话，回复固定的获取报告文案，`version` 加 1，状态不变。
  - 报告：用全部已提交的消息生成 `messageList`；成功后写入 `report_text` 和 `completed_at`，状态改为 `completed`。
- 降级：生成问题失败时使用固定问题；如果已经发出过 `delta`，先发 `reset` 事件，再把固定问题作为一个完整的 `delta` 发出。在消息的 `meta` 中记录 `fallback: true`。
- `app/services/consultation/runner.py`：进程内的轮次注册表。
  - 以 `(consultation_id, turn_id, attempt)` 为键，保存已产生的事件缓冲和一个条件变量；
  - 新的订阅者先回放缓冲中的事件，再接收实时事件；
  - 任务用 `asyncio.create_task` 创建，并放进一个集合中保持引用，防止被垃圾回收；
  - 任务完成 60 秒后清理对应的条目。
- 任务必须使用自己的 `AsyncSession`（从 `app/core/database.py` 的 session maker 创建），不能使用请求作用域的 session。
- `delta` 的 `offset` 按 Unicode 码点计数。
- `main.py` 的 lifespan 在关闭阶段等待进行中的任务，最多 60 秒。

**测试**：放在 T8 统一编写；本任务至少完成单元测试，覆盖受理条件、`TURN_ID_CONFLICT`、获取报告节点的行为和归档格式。

## T7 DitanBackend：API 与 SSE

**目标**：实现设计文档第 7 节的接口。

**改动**：

- 新建 `app/api/consultation.py` 和 `app/schemas/consultation.py`；在 `app/api/router.py` 中以 `prefix="/consultations", tags=["问诊"]` 注册。
- 非流式接口沿用现有的 `APIResponse` 信封（`success`、`message`、`data`）和 `BaseAPIException` 的异常风格。错误响应的 `data` 中带上业务错误码（如 `VERSION_CONFLICT`），并按设计文档附带快照或 `turn_id`。
- `POST /{id}/turns`：
  - 受理检查（第 1～3 步）在开始流式输出之前完成；检查失败时直接返回普通的 JSON 错误，不返回 SSE；
  - 检查通过后用 `StreamingResponse(media_type="text/event-stream")` 输出，响应头加 `Cache-Control: no-cache` 和 `X-Accel-Buffering: no`；

  - 事件名与数据结构与设计文档第 7 节完全一致；
  - 客户端断开时只取消订阅，不能取消任务。
- 所有接口都使用 `get_consultation_context`，并且只按 `org_id + id` 查找问诊，其他机构的问诊一律返回 404。
- 更新 `docs/API.md`，补充问诊接口说明。

**测试**：用 httpx 的 `ASGITransport` 读取 SSE，断言事件序列、心跳格式、各类错误的状态码与错误码，以及跨机构访问返回 404。

## T8 DitanBackend：M1 验收测试（全部使用假模型）

**目标**：证明设计文档 5.5 的恢复场景和第 15 节中与会话相关的检查项都成立。并发相关的用例必须在 PostgreSQL 套件中运行（SQLite 会忽略 `FOR UPDATE`）。

必须覆盖的用例：

1. 男性完整流程：开场 → 11 问 → 获取报告提示 → 报告，最终状态为 `completed`，`archive` 输出正确。
2. 女性 25 岁、女性 15 岁、女性 8 岁、性别缺失，各自的步骤序列正确。
3. 同一个 `turn_id` 重复提交，得到同一结果，消息不重复。
4. 同一个 `turn_id` 对应不同内容，返回 `TURN_ID_CONFLICT`。
5. 两个不同的 `turn_id` 并发提交（用 `asyncio.gather` 同时发出），一个成功，另一个得到 `SESSION_BUSY` 或 `VERSION_CONFLICT`。
6. 使用过期的 `base_version` 提交，返回 `VERSION_CONFLICT`，并附带快照。
7. 客户端在 SSE 中途断开，任务继续完成；随后用 `GET turn` 能查到结果。
8. 模拟进程崩溃：取消任务，并把 `deadline_at` 改到过去，用同一个 `turn_id` 重试，成功接管，`attempt` 等于 2。
9. 被接管后旧任务晚到并尝试提交：条件更新失败，结果被丢弃，消息不重复。
10. 卡住的进行中轮次已超时，客户端换了一个新的 `turn_id`：旧轮次被标为 `failed`，新轮次正常受理。
11. 生成问题时首个 token 之前失败，回复固定问题，`meta.fallback` 为 true。
12. 生成问题时中途失败，先收到 `reset` 事件，再收到固定问题。
13. 熔断：连续失败后，后续轮次不再调用模型。
14. 报告前患者继续说话：回复固定文案，状态不变，这段话出现在报告的 `messageList` 中。
15. 连续两次提交报告（不同 `turn_id`）：第二次得到 `REPORT_NOT_READY` 或 `CONSULTATION_CLOSED`，最终只有一份报告。
16. 报告失败（假模型在首个 token 前连续报错）：该轮标为 `failed`，状态仍为 `ready_for_report`，重试后成功。
17. 放弃后可以用同一个 `encounter_uuid` 重新创建；放弃时进行中的轮次被标为 `cancelled`，其结果不会提交。
18. 在开场之前用不同的 inputs 调用创建接口，inputs 被更新；开场之后再调用，inputs 不变。
19. 跨机构访问任何问诊接口都返回 404。

另外提供手工冒烟脚本 `scripts/consultation_smoke.py`：针对本地服务（`CONSULTATION_LLM_PROVIDER=fake`）跑一遍完整流程，并演示断线后重新接入。

**完成标准**：SQLite 和 PostgreSQL 两套测试全部通过；以上 19 条用例逐条对应到具体的测试函数，在汇报中列出对应关系。**到此为 M1，停下来等审查。**

## T9 DitanBackend：对照回放工具（M2）

**目标**：用真实对话比较新后端与 Coze 的输出，交业务方审阅。

**前提**：对照样本由仓库所有者从数据库导出并脱敏后提供，格式见下。执行代理不要访问生产数据库。

**样本格式**（JSON Lines，每行一条病历；所有者按此格式导出）：

```json
{
  "sample_id": "S001",
  "consultation_date": "2026-09-20",
  "inputs": {
    "patient": {"sex": "女", "birthday": "1994-05-01", "height_cm": 162, "weight_kg": 70, "target_weight_kg": null},
    "assessments": {"face": "…", "tongue": "…", "tongue_down": "…", "pulse": "…"}
  },
  "coze_conversation_log": "User: …\nAI: …",
  "coze_report": "…"
}
```

字段来源（DitanBackend 现有表）：

| 字段 | 来源 |
| --- | --- |
| `consultation_date` | `patient_medical_records.created_at` 的日期部分 |
| `sex`、`birthday` | `patients` |
| `height_cm`、`weight_kg`、`coze_conversation_log` | `pre_diagnosis_records` |
| `face`、`tongue`、`tongue_down`、`pulse` | `sanzhen_analysis_results` 的 `face`、`tongue_front`、`tongue_bottom`、`pulse` |
| `coze_report` | `sanzhen_analysis_results.diagnosis_result` |
| `target_weight_kg` | Ditan 没有保存，填 `null` |

脱敏要求：

- 去掉姓名和电话。注意 `coze_conversation_log` 中客户端生成的摘要行，以及 Coze 的提问（如"牛女士"），也可能包含姓名或电话，需要一并替换。
- 生日可以整体平移，但要保证按 `consultation_date` 算出的周岁不变。

已知偏差：`diagnosis_result` 目前最长 1024 字，超过的病历上传失败、没有入库，因此样本中的报告会偏短。

**改动**：

- `scripts/consultation_replay.py`：
  - 解析 `coze_conversation_log`：以 `User:` 开头的行是患者回答，每个回答前最近的一条 `AI:` 行是 Coze 的提问；以 `Status:` 开头的行，以及后面没有患者回答的开头介绍和摘要，都忽略；报告取 `coze_report`。
  - 对每条样本，以 `consultation_date` 为年龄基准日，在临时 SQLite 库中用真实模型（`CONSULTATION_LLM_PROVIDER=openai`）逐轮回放患者回答；
  - 输出一份 Markdown 报告，逐轮并排列出 Coze 的问题和新后端的问题，最后并排列出两份报告；
  - 标出步骤顺序或分支不一致的地方。
- 不修改提示词。若对照发现需要修改，在汇报中提出，由所有者决定是否发布 v2 提示词。

**完成标准**：工具能跑通至少一条样本；在汇报中附上报告的生成路径。

   - 只在 `version == 0` 时发送开场；
   - 待发轮次按设计文档 5.1 处理。
7. **ViewModel**：`DigitalHumanFlowState` 按设计文档第 11 节的对照表由快照推导；删除检测"获取报告"文案的逻辑；报告按钮改为发送 `kind=report`；`delta` 按 `offset` 去重后派发播报；派发任务绑定媒体 sessionid 和播放代次，媒体重连或打断后丢弃旧任务。
8. **归档**：问诊完成后调用 `archive`，把返回内容写入 `diagnosisResult` 和 `cozeConversationLog`，再走现有的 `PatientSubmissionCoordinator.saveAndUpload`。
9. **身份切换**：沿用现有的 generation guard，切换机构或退出登录后丢弃旧的回调和待发轮次。
